# xgrowth.tools 股票方向横纵分析报告

**项目：BEN 财经热点雷达**  
**研究日期：2026-08-16**  
**定位：面向中文财经内容团队的股票内容机会雷达，而非交易终端或买卖信号系统**

---

## 执行摘要

本项目真正值得借鉴的不是 xgrowth.tools 的颜色、卡片样式或导航名称，而是它对原始信息的二次组织方式：用户先看到“什么正在升温”，随后看到“为什么值得参与”，最后才进入原始帖子。这个顺序把数据采集系统转化成了内容生产工具。

股票方向的正确产品结构因此不是“新闻列表＋X 帖子列表＋行情列表”，而是：

> 发现加速事件 → 判断证据强度 → 观察股票与市场响应 → 形成内容角度 → 加入人工选题池

本轮实现已经停止增加新来源，保留现有新闻、X 与 TWSE 价量底座，将 `/ai-radar` 重构为中文优先的单列机会雷达，并新增兼容入口 `/stock-radar`。英文原文、长链接、采集错误和 Yahoo Finance 429 不再占据首页主视觉；Evidence 默认折叠，数据源诊断移到 `/radar`。

聚类审计说明了一个比 UI 更重要的事实：旧样本几乎没有真正聚类。任务启动时的只读重跑得到 92 条滚动窗口原始内容、84 条相关内容、84 个事件、0 个多条目簇和 0 个跨平台事件。原因不是单一阈值，而是实体词典覆盖不足、动作词过窄、相同公司的不同事件容易混淆、新闻与 X 当前样本缺少同题交叉。修复后，滚动窗口在另一时点为 94 条原始内容、63 条通过股票/宏观相关性门槛、59 个事件、2 个多条目簇、0 个跨平台事件。两个合并簇主要是同题转载或重复摘要，并不等于两个独立发布方确认。系统现在把这些状态直接暴露为真实指标，不再把“一条内容＝一个热点”包装成聚类成功。

最终结论：首版 MVP 应继续服务“Ben 能否在 10 秒内找到一个值得研究的题”，而不是追求全市场覆盖、伪实时、自动成稿或更高的原始抓取量。

## 一、纵轴：从社交监控工具到内容机会雷达

### 1. 原始阶段：信息获取是主要矛盾

早期的增长工具首先解决“我看不到足够多内容”的问题。产品价值来自聚合：把分散在不同账号、媒体和时间线里的帖子集中到同一页面。这个阶段的典型页面是 feed，排序依据通常是发布时间、点赞或浏览量。

这种结构在数据量较小时有效。一旦来源数量增加，feed 会迅速退化成新的信息噪音。用户仍然需要自己完成实体识别、事件归并、可信度判断和内容角度提炼。因此，抓取能力越强，页面越可能变得不可读。

旧版 BEN Radar 正处于这个矛盾中：采集已经能拿到新闻、X 与 TWSE 历史价量，但首页把采集健康、原始计数、英文标题、规则分析、Evidence 和行情异动同时铺开。它证明了“系统抓到了什么”，却没有首先回答“编辑现在应该看什么”。

### 2. xgrowth.tools 的关键跃迁：从帖子转向生命周期

xgrowth.tools 的公开产品结构把内容分为不同生命周期，并使用传播速度而不是累计浏览量来排序。其 viral tweets 页面将 0–4 小时内容定义为潜力阶段、4–24 小时定义为爆发阶段；tweet ideas 页面进一步把共同讨论聚成话题，展示热度、近一小时变化、参与创作者、关联帖子、首次出现和最后活跃时间，并提供 24h / 12h / 6h 时间切换。

这一步改变了用户的认知单位：

- 原先的单位是“一条帖子”；
- 后来的单位是“一个正在变化的话题”；
- 用户行动也从“阅读”变为“判断是否参与”。

参考页面：[xgrowth.tools](https://xgrowth.tools/)、[Viral Tweets](https://xgrowth.tools/viral-tweets)、[Tweet Ideas](https://xgrowth.tools/tweet-ideas)。

### 3. 股票版的下一次跃迁：从热度转向可核实内容机会

社交增长产品可以把传播本身当作价值，但财经内容不能。股票话题具有四个额外约束：

1. 同一家公司一天内可能同时发生财报、融资、监管和产品事件，不能只按 ticker 合并。
2. 单一大号转发不等于多来源确认，相同 publisher group 的转载也不能重复计数。
3. 价格变化可能发生在新闻之前、之后或毫无关系，不能把相关性写成因果。
4. 中文团队需要先读中文标题和摘要，但规则生成不能冒充准确翻译。

因此股票版不应复制“最热帖子榜”，而应建立一个 Evidence-first 的编辑工作流：

- 首页只展示规则中文标题、简短摘要、来源广度、相关股票、可能影响和内容角度；
- 原始英文、完整链接和事实核实事项收进 Evidence；
- 页面明确区分官方、新闻和 X 观点；
- 内容机会分表示“值得研究”，不是“值得买入”；
- 数据源失败保留真实状态，但不抢占编辑首页。

## 三、交叉洞察：哪些能借鉴，哪些不能照搬

### 可借鉴的五个机制

**1. 生命周期分层。** xgrowth.tools 使用 0–4h 与 4–24h；本项目在最新产品决策中采用 24H / 12H / 6H 浏览窗口，并保留事件趋势 NEW / HEATING / STEADY / COOLING。时间窗口用于浏览，趋势用于解释变化，两者不混为一谈。

**2. 速度优先。** 累计浏览量天然偏向旧帖子和大账号。BEN Radar 优先读取相邻互动快照；有浏览量时计算浏览增量率，缺失时退回加权互动速度。页面显示“传播/小时”和加速度，但不宣称全网速度。

**3. 话题聚合。** 共享规范化链接可直接聚类；否则在 36 小时内按“实体＋动作＋文本相似”或“主题＋动作＋文本相似”分级判断。相同 publisher group 和转帖不增加独立确认数。

**4. 信息密度。** 首页单卡只保留中文标题、摘要、四个核心计数、相关股票、影响解释、内容机会和折叠 Evidence。完整原文不再使用最大字号。

**5. 行动导向。** 用户可以加入选题池、忽略、写备注、恢复以及导出 JSON/CSV。首版只写浏览器 localStorage，避免在无认证公网隧道上增加服务器写接口。

### 不能照搬的四个部分

**1. 不能把浏览量速度当作唯一热度。** 财经内容还需要独立来源广度、Evidence 质量和市场响应。

**2. 不能把同一 ticker 当作同一事件。** “NVIDIA 投资数据中心”和“NVIDIA 财报指引”即使在同一天也必须分开。

**3. 不能用英文原文冒充中文产品。** 若能规则化提炼，显示“规则中文摘要”；若无法可靠提炼，首页显示“中文摘要生成中”，原文只进入 Evidence。规则摘要不标成 AI 翻译。

**4. 不能用跨平台为零逼迫过度聚类。** 当前窗口新闻与 X 没有可靠同题重合时，0 就是正确结果。后续应通过来源设计和采集时点提高自然重合，而不是降低阈值制造漂亮数字。

## 四、聚类问题的根因审计

### 1. 旧规则为什么几乎不聚类

旧 `_same_event` 除共享链接外，要求两条内容同时满足：

- 有共同股票实体；
- 有共同事件动作；
- 发布时间相差不超过 36 小时；
- 文本 Jaccard 相似度至少 0.12。

这个逻辑表面严格，实际有三个覆盖缺口：

- 实体词典只有少数台股和 `NVDA/AAPL/MSFT/TSLA`，当前 X 样本 46 条里只有 1 条命中实体；
- “weighs”“in talks”“supply”“data center”等常见财经表达没有进入动作词；
- 没有实体但明显属于利率、能源、地缘政治或数字资产的内容无法形成稳定主题签名。

任务开始时的滚动窗口诊断显示：新闻 46、X 46，最终 84 个相关事件；新闻实体命中 14 条、X 实体只命中 1 条；没有任何多条目聚类。这证明主要矛盾不是 CSS，而是语义入口过窄。

### 2. 本轮修复

本轮扩展了台股核心股与美股核心科技股别名，加入边界匹配，避免 `arm` 在普通英文单词里误识别为 ARM；动作词扩展到资本动作、订单/供应链、数据中心、回购、突发事件与价格异动；主题扩展到 AI/半导体、宏观、公司财报、政策关税、能源原物料、地缘政治和数字资产。

新的分级聚类规则是：

1. 共享规范化外链：直接合并；
2. 共同实体＋共同动作：相似度至少 0.16；
3. 共同实体：相似度至少 0.20；
4. 共同主题＋共同动作：相似度至少 0.16；
5. 没有语义锚点：只有高度相似（至少 0.42）才合并。

阈值曾在回归中短暂设为 0.08，但把两条不同的 NVIDIA 投资故事合并。真实样本检查后已收紧到 0.16。这一过程说明，聚类质量必须通过“合并了什么”而不是只看压缩率验收。

### 3. 当前真实结果应如何解释

当前滚动窗口因为时间不断变化，原始条数会略有波动。最终回归的一次结果为：

| 指标 | 结果 | 含义 |
|---|---:|---|
| 原始新闻＋X | 94 | 采集窗口内全部输入 |
| 通过财经相关性门槛 | 63 | 有股票实体、财经动作或财经主题 |
| 聚类事件 | 59 | 首页候选事件总量 |
| 合格内容压缩率 | 6.3% | 只对 63 条合格内容计算 |
| 多条目事件 | 2 | 可能包含同来源转载或重复摘要 |
| 多独立发布方事件 | 0 | 当前没有两个 publisher group 的确认 |
| 新闻＋X 事件 | 0 | 当前没有可靠跨平台同题重合 |

这仍不是理想的聚类密度，但比“93→85”更可解释：系统先过滤掉不适合股票内容的内容，再把确实相同的条目合并，同时明确告诉用户独立确认仍为零。

## 五、股票版信息架构

### 页面第一屏

- 主问题：“过去 24 小时，市场正在讨论什么？”
- 运行状态、最后更新时间、数据源状态入口；
- 监测池、行情时点、不构成投资建议、聚类压缩率；
- “机会雷达 / 聚合快讯”模式；
- 今日摘要：最高机会、升温最快、独立来源最多；
- 分类：全部、台股、美股、AI 科技、宏观、其他；
- 时间：24H、12H、6H；
- 来源：全部、新闻、X；
- 排序：综合热度、增长最快、讨论最多、最新出现、市场影响最大。

### 事件卡

事件卡把用户决策压缩成六个问题：

1. **这是什么？** 规则中文标题和一句摘要。
2. **它在什么阶段？** 新出现、升温、持续或降温。
3. **有多少证据？** 独立发布方、新闻来源、X 账号。
4. **跟哪些股票有关？** ticker 标签和已匹配的 TWSE 价量响应。
5. **为什么值得做？** 保守的可能影响说明。
6. **怎么做内容？** 内容机会分、推荐形式和推荐角度。

Evidence 默认折叠，展开后才看到原始英文、完整链接、时间和核实清单。这样首页保留决策密度，详情仍保持可追溯。

### 本地选题池

首版使用版本化键名 `ben-stock-radar.topic-queue.v1`，存储 event ID、中文标题、分数、相关股票、状态、备注和更新时间。JSON/CSV 导出均在浏览器生成；CSV 对以 `= + - @` 开头的单元格加前缀，降低表格公式注入风险。

## 六、评分与趋势的解释边界

当前热度分由五个透明维度组成：新鲜度、传播加速度、独立来源广度、Evidence 质量和市场响应。没有匹配行情时，市场响应保持 0，不生成替代分数。

Evidence 质量遵循以下原则：新闻＋X 交叉最高；新闻来源次之；官方或高权威 X 再次；普通单一 X 观点最低。这个分数不是事实真假概率，只表示当前 Evidence 结构是否更适合进入编辑研究。

趋势规则：首次进入 2 小时内为 NEW；相邻速度提高至少 20% 为 HEATING；下降至少 20% 或 6 小时无实质更新为 COOLING；其余为 STEADY。没有足够快照时不虚构加速度。

内容机会分综合热度、Evidence、股票实体和主题清晰度。它只回答“是否值得内容团队继续研究”，不回答“股票会上涨还是下跌”。

## 七、验收结果

### 功能验收

- `/ai-radar` 与 `/stock-radar` 均可读取同一机会雷达；
- 24H / 12H / 6H、分类、来源、五种排序可组合；
- 中文标题优先，英文只在折叠 Evidence 中；
- Yahoo Finance 429 和新闻采集运行状态位于 `/radar`；
- 选题池加入、忽略、备注、恢复、JSON/CSV 导出全部为浏览器本地操作；
- 页面不提供买卖点、自动发帖、自动成稿或多人实时协作声明。

### 视觉验收

- 1280px 桌面视口：文档宽度小于视口宽度，无横向溢出；首张事件卡高度约 386px；
- 390px 移动视口：卡片宽度适配，文档无横向溢出；分类栏使用自身横向滚动；
- Evidence 默认关闭，移动端展开后仍无页面级横向溢出；
- “加入选题池”后备注区出现，状态计数更新；
- 浏览器控制台 error/warning 为 0。

## 八、下一阶段建议

### 立即做

1. 让 Ben 用真实任务完成 10 秒选题测试，记录他点击的第一张卡、放弃原因和最终是否出稿。
2. 为误聚类、漏聚类建立小型标注集，每周固定复盘 30–50 对，不用压缩率代替质量。
3. 优先补充公司别名、事件动作和主题词，避免立即引入黑箱模型。
4. 将“中文摘要生成中”条目列入人工规则补全队列，统计最常见缺口。
5. 继续采集互动快照，至少三次快照后再稳定使用加速度趋势。

### 条件满足后再做

- Twelve Data 商业授权和 Key 明确后，再接美股 OHLCV 与市场状态；
- SEC User-Agent 联系身份明确后，再接 EDGAR 官方催化；
- 有真实编辑使用记录后，再决定是否接模型生成标题或草稿；
- 有认证与权限方案后，再考虑服务器端共享选题池。

### 明确不做

- 不为了跨平台数字好看而降低聚类阈值；
- 不把 EOD 行情显示成实时；
- 不在首页展开采集错误和长 URL；
- 不把规则中文摘要标成 AI 翻译；
- 不自动发布，不自动互动，不输出投资建议。
