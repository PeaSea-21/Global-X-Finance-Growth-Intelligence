# BEN 20 频道每日热点业务需求分析

- 日期：2026-08-18
- 输入：Ben 当日录音转写、当前仓库代码/配置/已验证产物
- 状态：`SOURCE_REQUIREMENT_ANALYSIS`；GPT 方案已复核，改进后的实施建议见 `BEN_Radar_Channel_Driven_最优业务方案_v2_2026-08-18.md`
- 本文不等于技术实施批准，不改变现有 Radar 规则、数据库或来源权限

## 1. 一句话结论

Ben 要的不是一个把新闻、股票和成交量放在一起的“大表”，而是一个以 **“频道 × 当天”** 为主键的选题决策系统：系统先从市场、公司、新闻、日历和讨论热度中找出值得讲的变化，再把它们分配给最合适的频道；负责人打开频道后，应在几十秒内看到今天最值得讲的 5 个以上候选、每个候选为什么入选、证据是什么、数据属于哪个市场时段，并能直接做出采用或放弃决定。

## 2. 录音真正否定了什么

Ben 明确否定的是以下产品形态：

1. 把所有新闻、股票和数据混在一页，仍要求人自己逐条阅读和筛选。
2. 只按统一热度排榜，不理解不同频道的受众、定位和可讲范围。
3. 只告诉用户“发生了什么”，不解释“为什么今天值得这个频道讲”。
4. 把台股和美股放在同一个“今天”口径里，忽略开盘、收盘和时差。
5. 为追求实时而接入大量昂贵数据，但没有先证明它能提高选题效率。
6. 让负责人看几个小时的数据，最后仍无法快速选出要生产的内容。

因此，评价产品有没有用的标准不是“采了多少条”，而是 **是否减少了人工筛选、是否选得准、是否能解释、是否能直接进入内容生产**。

## 3. 核心业务对象要换掉

当前常见系统以 `NewsItem`、`Stock` 或 `Event` 为首页单位；Ben 的业务应以 `ChannelDailyBrief` 为首页单位。

```text
原始来源 / 官方行情 / 公司公告 / 财报日历 / X 与媒体讨论
                    ↓
              可审计事件池 Event
                    ↓
       时段有效性 + 变化强度 + Evidence 闸门
                    ↓
       频道画像 ChannelProfile 与事件匹配
                    ↓
      ChannelTopicAssignment（频道-选题匹配）
                    ↓
   每频道今日 5–8 个候选 + 理由 + Evidence + 切角
                    ↓
          人工采用 / 忽略 / 进入生产队列
```

一个真实事件可以匹配多个频道，但每个频道必须有不同且符合定位的讲法。例如同一项 AI 芯片公司财报，可以分别进入美股科技、半导体供应链、台股映射和全球宏观频道；系统不能把同一段文案复制四次。

## 4. “热点”在本业务中的定义

热点不是“涨幅榜”，也不是“转发量最高”。一个候选至少要回答以下问题：

| 判断维度 | 必须回答的问题 |
|---|---|
| 发生变化 | 相比此前、预期或历史基线，什么发生了明显变化？ |
| 频道匹配 | 为什么这个变化适合这个频道，而不是所有频道通发？ |
| 时间有效 | 它属于台股盘前/盘中/收盘后，还是美股上一交易日/盘前/收盘后？ |
| Evidence | 哪些事实可由官方、公司或合格来源核验？哪些仍是 `OPINION / UNKNOWN`？ |
| 话题性 | 普通受众为什么会关心、争论或需要解释？ |
| 可生产性 | 能否形成清楚的标题、核心问题、数据点和验证任务？ |
| 新鲜度 | 是今天的新变化、持续发酵，还是已经过期的旧闻？ |

候选先过硬闸门，再做频道内排序。建议排序披露以下分量，而不是只显示一个不透明总分：

- `CHANNEL_FIT`：与频道受众、市场、行业和内容类型的匹配度。
- `CHANGE_STRENGTH`：价格/量能、公告、预期、政策或舆论相对基线的变化。
- `EVIDENCE_QUALITY`：官方/公司 Evidence、独立来源数、冲突和缺失状态。
- `TIME_RELEVANCE`：对当前市场时段是否仍然有效。
- `TALKABILITY`：是否存在清晰矛盾、反差、未知点或解释价值。
- `NOVELTY`：与本频道近 30 天已采用选题的重复程度。

## 5. 20 个频道与“每频道 5 个以上”的正确理解

20 个频道每天至少 5 个候选，意味着每天至少产生 **100 个频道-选题匹配位**，不等于每天必须找到 100 个互不相同的真实事件。

建议每个频道输出：

- 5 个主候选：默认首页直接显示，可立即判断。
- 0–3 个备选：主候选不合适时展开。
- 1 个“今日最该讲”：必须给出最强入选理由和主要风险。
- 1 个“继续观察”：条件未满足，不伪装成已确认热点。

不能为了达到 5 条硬填旧闻或弱事实。若某频道只有 3 条达到 Evidence 和匹配标准，页面应显示 `3/5，今日强热点不足`，同时说明缺口来自来源不足、市场未开盘、事件重复还是 Evidence 不足。业务目标是长期让大多数频道达到 5–8 条，不是让系统编造满额。

### 频道画像最低字段

当前录音和仓库都没有出现一份可确认的“20 个输出频道”清单。下一步收到的频道表至少需要以下字段：

```text
channel_id / channel_name / channel_summary
target_audience / primary_market / secondary_market
preferred_sectors[] / preferred_topic_types[] / excluded_topics[]
content_formats[] / language / depth / risk_tolerance
required_evidence_level / allowed_opinion_sources
daily_candidate_target / priority
recent_30d_adopted_topics[] / do_not_repeat_patterns[]
```

这里的“输出频道”不能与仓库中的 29 个 X 监控账号、23 个实时来源条目、1 个 YouTube 来源或 Stock Workbench 的 20 只股票混为一谈。

## 6. 市场时间必须成为业务规则

第一阶段接受收盘数据是合理的，关键是页面必须明确“数据属于哪个完成交易时段”。

| 市场场景 | 页面可用口径 | 禁止表达 |
|---|---|---|
| 台股盘前 | 上一完整交易日 + 盘前公司/政策事件 | 把上一日收盘异动写成今日盘中异动 |
| 台股盘中 | 只有已授权且时间戳清晰的数据才可称盘中 | 用延迟或日频数据冒充实时 |
| 台股收盘后 | 当日完整 EOD、成交量、历史基线、公告 | 在市场未收盘前提前使用完整日数据 |
| 亚洲早间看美股 | 美国上一完整交易日/刚收盘数据 | 用台北自然日直接标记为美股“今日行情” |
| 美股盘前/盘中 | 第一阶段可暂不做；显示能力未接入 | 用新闻推断实时价格或成交量 |
| 非行情事件 | 采用原始发布时间、有效期和来源时区 | 把旧闻因刚抓取而标成新事件 |

实现上，每条候选至少保存 `market`、`source_published_at`、`market_session_date`、`session_state`、`data_as_of`、`freshness_state`。美国和台湾可以共用引擎，但时钟、交易日历和可用数据窗口必须由各自 Market Pack 表达。

## 7. Ben 每天真正应该看到的卡片

每个频道首页先显示 5–8 张紧凑卡片，而不是原始表格。单卡最低信息如下：

1. **一句话选题**：发生了什么变化。
2. **为什么今天讲**：变化、时间、声量或预期差。
3. **为什么适合本频道**：频道标签命中和受众价值。
4. **关键事实**：最多 3 个数字/事实，均带日期和 Evidence。
5. **可讲切角**：2–3 个不同选题方向，不直接生成冗长正文。
6. **建议标题**：2–3 个工作标题，明确为选题草案而非事实。
7. **相关股票/行业**：市场限定 ID，禁止只显示裸 ticker。
8. **市场时段**：例如 `台股 2026-08-17 收盘后` 或 `美股上一交易日收盘`。
9. **风险与未知**：催化剂未证实、来源冲突、数据未到等。
10. **操作**：采用、备选、忽略、查看 Evidence；采用后才进入生产流程。

首页默认不展示长篇原文、爬虫状态、全部指标或复杂图表。Evidence、K 线和来源诊断应在展开后使用。

## 8. 当前仓库与目标业务的差距

### 已有且可复用

- 台股 TWSE/TPEx 最新完整收盘数据、历史基线和可解释异常 Top20。
- 真实 EOD OHLCV、量比、20/40 日突破、价格/量能共振和连续入榜上下文。
- 新闻/X 事件池、去重、来源组、Evidence 链路、过期/失败状态和本地选题队列。
- 中文优先机会卡、选题切角、透明理由和人工采用/忽略入口。
- 一套尚未按真实账号校准的 5 类 Style Pack 原型。

### 当前缺失

- 权威的 20 个输出频道清单、简介、标签、受众和禁区。
- `Event → Channel` 匹配层与每频道每日排序。
- 每频道 5–8 条候选的配额、去重和短缺状态。
- 美股合格 EOD 数据接入、交易日历和时段状态。
- 财报/公司事件日历的稳定来源与频道路由。
- 采用后内容生产、认领、防撞、审核和 1H/6H/24H 反馈闭环。
- 用 Ben 真实采用/拒绝记录校准排序的业务 Gold set。

### 不能误报为已完成

- 当前 20 只股票不是 20 个内容频道。
- 当前 29 个 X 账号是发现来源，不是输出频道。
- 当前行业映射位于未提交工作树中，尚不能作为本次任务已验证能力。
- 美国来源注册、行情覆盖和生产可用性仍为 `UNKNOWN / NEEDS_CONFIRMATION`。

## 10. 最合理的阶段顺序

### 阶段 A：把业务说清楚

拿到 20 个频道表和 GPT 业务方案，逐频道确认：定位、市场、标签、每天数量、禁区、谁负责、什么叫“可用”。先形成频道画像 v0.1，不写自动生成代码。

### 阶段 B：用现有台股 EOD 做真实样板

只用已有台股收盘异常、公司公告和当前事件池，选择 3 个代表频道做 `Event → Channel` 匹配，真实生成每频道 5–8 条候选。Ben 连续试用 3–5 个交易日，记录采用、拒绝和原因。

### 阶段 C：扩展到 20 个频道

固定频道画像、匹配解释、短缺状态和去重规则；上线 20 频道日视图。此时每天目标是 100 个匹配位，不以 100 个独立事件为目标。

### 阶段 D：补美股 EOD 与日历

在来源授权、成本和时区口径确认后，接入美股收盘数据和财报日历。台股与美股共用核心流程，但按各自完整交易时段生成 Brief。

### 阶段 E：接入生产与反馈

负责人采用候选后，再进入标题/提纲/草稿、认领、防撞和审核；保存人工发布记录及 1H/6H/24H 表现。用真实采用率和拒绝原因校准频道匹配，不用页面浏览量代替业务验收。

## 11. 业务验收标准

最终工具至少应满足：

1. 负责人打开任一频道，10 秒内能指出“今天最该讲什么”。
2. 30 秒内能看到入选原因、关键 Evidence、市场时段和主要风险。
3. 60 秒内能将候选保存到生产队列并添加备注。
4. 每频道目标 5–8 条合格候选；不足时诚实显示数量与原因。
5. 100% 候选显示 `data_as_of` 与市场时段，不把旧闻或上一交易日冒充当前实时。
6. 100% 财经事实可回链 Evidence；`OPINION / UNKNOWN / SOURCE_CONFLICT` 不被补成事实。
7. 同一频道近 30 天明显重复选题可见；跨频道复用必须显示不同频道匹配理由。
8. Ben 的采用率、拒绝原因和“漏掉的重要选题”可以按频道复盘。
9. 在没有真实美股数据、来源授权或频道资料时，页面显示能力缺口，不生成假内容。

## 12. 下一轮审查 GPT 方案时的评分表

收到 GPT 方案后，应逐项打分，而不是直接照方案开发：

| 评分项 | 关键问题 |
|---|---|
| 业务主键 | 是否真正以“频道 × 当天”为首页，而不是继续做统一信息池？ |
| 20 频道可配置性 | 是否读取频道简介/标签，支持版本和禁区？ |
| 每频道 5+ | 是否说明 100 个匹配位如何产生、去重和短缺？ |
| 选择解释 | 是否能说明为什么入选、为什么适合该频道、为什么是现在？ |
| 市场时钟 | 是否正确区分台股/美股交易日、盘前/盘中/收盘后？ |
| Evidence | 是否保留事实、观点、未知、冲突和来源权利边界？ |
| 人的效率 | 是否能在 10/30/60 秒完成选择、核验和保存？ |
| 现有资产复用 | 是否复用当前 EOD、Anomaly Engine、事件池和 Evidence，而不是重建？ |
| 分阶段交付 | 是否先用真实台股 EOD 验证，再扩 20 频道和美股？ |
| 可学习闭环 | 是否记录采用/拒绝/漏题，而不是只收集点击或浏览？ |

## 13. 当前需要用户下一步提供的材料

1. GPT 给出的完整业务方案。
2. 20 个输出频道的表格，至少包含名称、简介、主要市场、主要标签和不能讲的内容。
3. 若表中未包含：每个频道期望的每日候选数、内容负责人和优先级。
4. 最好再给 3–5 个频道各 5 条“过去认为值得讲”和“不值得讲”的真实样例，用于建立第一版业务 Gold set。

在这些材料到齐前，可以确定产品方向和数据契约，但不能诚实地声称已经完成 20 频道匹配规则或最终最优方案。
